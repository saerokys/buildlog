# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 사용하는 기술

| 구분 | 기술 | 비고 |
| --- | --- | --- |
| 백엔드 | Python, FastAPI | 화면에 필요한 데이터를 주고받는 API 서버 |
| 프론트엔드 | React (Vite) | 브라우저 화면, 백엔드 API를 호출 |
| 데이터베이스 (개발·테스트) | SQLite | `database/buildlog.sqlite3`, 자동 테스트는 별도 임시 DB 사용 |
| 데이터베이스 (실제 서비스) | Supabase (PostgreSQL) | Phase 13에서 연결 |
| 데이터베이스 접근 | SQLAlchemy | 같은 코드로 SQLite와 PostgreSQL을 모두 사용 |
| 테이블 변경 관리 | Alembic | 테이블 구조 변경(마이그레이션)을 파일로 기록 |

### 사용할 외부 패키지

아래 목록 외의 패키지는 추가하기 전에 먼저 확인합니다.

- 백엔드: `fastapi`, `uvicorn`, `sqlalchemy`, `alembic`, `pydantic-settings`, `pwdlib[argon2]`(비밀번호 암호화), `pyjwt`(로그인 상태 확인), `pytest`, `httpx2`(테스트용)
- Supabase 연결 시 추가: `psycopg`(PostgreSQL 연결)
- 프론트엔드: `react`, `react-dom`, `react-router`, `vite`, `@vitejs/plugin-react`(Vite에서 React 사용), `vitest`, `@testing-library/react`, `@testing-library/dom`(`@testing-library/react`가 필요로 함), `jsdom`(테스트용 가상 브라우저)

### 주요 구조 결정

- **회원 인증**: FastAPI가 직접 처리합니다. 비밀번호는 암호화해서 저장하고, 로그인하면 로그인 토큰을 `HttpOnly` 쿠키에 담아 브라우저에 줍니다. 화면의 JavaScript는 이 토큰을 읽을 수 없습니다.
- **Supabase의 역할**: 데이터베이스(PostgreSQL)로만 사용합니다. Supabase Auth와 Supabase 자동 API는 사용하지 않습니다. 모든 데이터 요청은 FastAPI를 거치고, 권한 검사도 FastAPI에서 합니다.
- **화면과 서버 연결**: 개발 중에는 React 개발 서버가 `/api`로 시작하는 요청을 FastAPI로 전달합니다. 화면과 서버가 같은 주소처럼 동작하므로 쿠키 설정이 단순해집니다.
- **운영자**: 사용자 정보에 운영자 여부를 저장합니다. 운영자 지정은 서버에서 실행하는 명령으로만 할 수 있고, 운영자만 신고 목록 API와 신고 목록 화면을 사용할 수 있습니다.

## 3. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. FastAPI에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 프론트엔드에는 비밀값을 넣지 않습니다. 프론트엔드 환경 변수는 브라우저에 그대로 공개되기 때문입니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, `node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- 데이터베이스 코드는 SQLite 전용 기능을 쓰지 않고, Supabase(PostgreSQL)에서도 같은 결과가 나오게 작성합니다.

## 4. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ .env.example        # 필요한 환경 변수 이름과 설명만 기록, 비밀값 없음 (실제 값은 backend/.env)
│  ├─ requirements.txt
│  ├─ alembic.ini
│  ├─ alembic/            # 테이블 변경 기록(마이그레이션)
│  ├─ app/
│  │  ├─ main.py          # FastAPI 시작점과 라우터 연결
│  │  ├─ core/            # 설정, DB 연결, 로그인 토큰·비밀번호 처리
│  │  ├─ accounts/        # 회원가입, 로그인, 닉네임
│  │  ├─ records/         # 공부 기록, 할 일, 오류 기록, 공개 기록
│  │  ├─ community/       # 댓글, 좋아요, 신고
│  │  └─ scripts/         # 운영자 지정 같은 관리 명령
│  └─ tests/              # 백엔드 자동 테스트
├─ frontend/
│  ├─ package.json
│  ├─ vite.config.js      # /api 요청을 FastAPI로 전달
│  ├─ index.html
│  └─ src/
│     ├─ main.jsx
│     ├─ App.jsx          # 화면 경로 연결
│     ├─ api/             # 백엔드 API 호출 함수
│     ├─ pages/           # 화면 단위 컴포넌트
│     ├─ components/      # 여러 화면에서 쓰는 부품
│     └─ styles/          # CSS
├─ database/
│  └─ buildlog.sqlite3    # 개발용 데이터 파일, Git 제외
└─ docs/                  # 요구사항, 동작 설명서, 개발 문서
```

각 앱(`accounts`, `records`, `community`)은 같은 파일 구성을 사용합니다.

- `models.py`: 데이터베이스 테이블
- `schemas.py`: API로 주고받는 데이터 모양과 입력 검사
- `service.py`: 저장, 조회, 상태 변경 같은 실제 처리
- `router.py`: API 주소

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 설치된 Python, Node.js, npm 버전을 확인합니다.
4. 확인한 버전과 호환되는 FastAPI, SQLAlchemy, Alembic, React, Vite의 안정 버전을 정합니다.
5. SQLite가 Python 환경에서 사용 가능한지 확인합니다.
6. 개발 서버 주소, 데이터베이스 파일 위치, 환경 변수 이름을 정리합니다.
7. 테스트 명령과 서버 실행 명령을 문서에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python, Node.js, npm 실행 여부와 버전을 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

#### 목표

기능 없이도 백엔드와 프론트엔드 개발 서버가 실행되고, 화면에서 백엔드 응답을 볼 수 있게 합니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 준비합니다.
2. 백엔드 기본 패키지를 설치하고 정확한 버전을 `backend/requirements.txt`에 기록합니다.
3. `backend/app/main.py`에 FastAPI 앱을 만들고 상태 확인 API(`/api/health`) 하나만 연결합니다.
4. 설정값을 환경 변수에서 읽는 `backend/app/core/config.py`를 만듭니다.
5. 데이터베이스 주소를 환경 변수로 받고, 개발 기본값을 `database/buildlog.sqlite3`로 둡니다.
6. `frontend`에 Vite로 React 프로젝트를 만들고 정확한 버전을 `package.json`에 기록합니다.
7. Vite 개발 서버가 `/api` 요청을 FastAPI로 전달하도록 설정합니다.
8. 기본 화면에서 상태 확인 API를 호출해 결과를 보여줍니다.
9. `.env.example`에 환경 변수 이름만 기록합니다.
10. SQLite 파일과 테스트 중 생성되는 파일을 `.gitignore`에 보완합니다.
11. 이 Phase에서는 아직 테이블을 만들지 않습니다. 사용자 모델을 먼저 만들어야 하기 때문입니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/app/main.py`
- `backend/app/core/config.py`
- `backend/tests/test_health.py`
- `frontend/package.json`
- `frontend/vite.config.js`
- `frontend/index.html`
- `frontend/src/main.jsx`
- `frontend/src/App.jsx`
- `frontend/src/styles/base.css`
- `.env.example`
- `.gitignore`

#### 확인 방법

- FastAPI 개발 서버가 오류 없이 시작되는지 확인합니다.
- React 개발 서버가 오류 없이 시작되는지 확인합니다.
- 브라우저의 기본 화면에 상태 확인 API 응답이 보이는지 확인합니다.
- 상태 확인 API 자동 테스트가 통과하는지 확인합니다.
- 비밀 설정값, SQLite 파일, `node_modules`, `.venv`가 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 두 서버와 기본 화면이 정상 실행되어야 합니다.
- 사용자 모델을 만들기 전에는 테이블을 만들지 않습니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. SQLAlchemy 데이터베이스 연결을 `backend/app/core/database.py`에 만듭니다.
2. Alembic을 준비하고 데이터베이스 주소를 환경 변수에서 읽게 합니다.
3. `accounts` 앱에 사용자 모델을 만듭니다.
   - 이메일, 암호화된 비밀번호, 닉네임, 운영자 여부, 가입 날짜·시간
4. 이메일은 필수이며 중복되지 않게 데이터베이스 제약을 둡니다.
5. 닉네임은 필수이며 중복되지 않게 데이터베이스 제약을 둡니다.
6. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용하는 검사 함수를 만듭니다.
7. 비밀번호는 `pwdlib`의 Argon2로 암호화해서 저장합니다.
8. 새 사용자의 운영자 여부 기본값은 `아님`으로 둡니다.
9. 첫 마이그레이션을 만들고 빈 SQLite 데이터베이스에 적용합니다.
10. 자동 테스트는 매번 새로 만든 임시 SQLite 데이터베이스에서 실행하게 합니다.
11. 사용자 모델 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/app/core/database.py`
- `backend/app/core/security.py`
- `backend/app/accounts/models.py`
- `backend/alembic.ini`
- `backend/alembic/`
- `backend/tests/conftest.py`
- `backend/tests/accounts/test_models.py`
- `backend/requirements.txt`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.
- 자동 테스트가 개발용 `database/buildlog.sqlite3`를 건드리지 않는지 확인합니다.

#### 완료 조건

- 첫 마이그레이션과 사용자 모델 테스트가 모두 통과해야 합니다.
- 사용자 모델을 다시 바꾸기 위해 데이터베이스를 지워야 하는 문제가 없어야 합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. 회원가입 API를 만듭니다.
2. 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 로그인 API를 만듭니다. 성공하면 로그인 토큰을 `HttpOnly` 쿠키로 보냅니다.
4. 이메일이나 비밀번호가 틀리면 어느 쪽이 틀렸는지 구분하지 않고 같은 안내를 보냅니다.
5. 현재 로그인한 사용자를 확인하는 공통 함수를 만들고, 로그인이 필요한 모든 API에 사용합니다.

| 프론트엔드 서버 실행 | `frontend/` | `npm run dev` |
| 프론트엔드 테스트 | `frontend/` | `npm test` |

### 7.6 해당 Phase 시작 전에 정할 내용

기능 범위의 충돌은 아니지만 `spec.md`에 정해지지 않아 구현 전에 정해야 하는 내용입니다.

| 정할 내용 | 필요한 Phase |
| --- | --- |
| 내 기록 홈 화면에 어떤 기록을 보여줄지 (PRD 6.3의 "핵심 기록"). Phase 3에서는 인사말과 계정 설정 링크만 둠 | Phase 5 |
| 검색할 때 영문 대소문자를 구분할지 | Phase 5 |
| 기록을 삭제하면 그 기록의 댓글·좋아요·신고를 어떻게 할지 | Phase 9 |
| 댓글을 삭제하면 그 댓글의 신고를 어떻게 할지 | Phase 11 |

## 8. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 결과와 확인 내용을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
